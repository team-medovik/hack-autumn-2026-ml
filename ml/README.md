# Подготовка данных для ML: до обучения

Модель пока **не обучалась**, CatBoost не установлен и не подключён к API.
Этот модуль готовит проверяемую таблицу признаков и меток на демонстрационной истории
из `examples/risk/vps-business/history.json`. Реальные только публичные тарифы;
поведение, договоры и исходы синтетические. Число строк не доказывает качество будущего прогноза.

## Назначение

ML дополняет F1–F5: предсказывает непродление конкретной VPS **до истечения оплаченного
срока**. Для `prolong_wait` и уже просроченных услуг остаются правила. Предупреждения
качества данных в существующем риск-движке не отменяются этим отбором обучающих строк.

Будущее обучение — Logloss, без подмены целевой метки баллом правил. Денежная
приоритизация отдельно: сумма `p(loss) × monthlyRevenue` по уникальным VPS клиента.
Здесь нет предсказанных вероятностей, оценок качества или готовой сортировки клиентов.
Месячная выручка для этой формулы не обнуляется по порогам F1–F5.

## Запуск

Из корня репозитория, Python 3, без сторонних библиотек:

```sh
python3 examples/risk/vps-business/validate.py
python3 ml/prepare_dataset.py
python3 -m unittest discover -s ml/tests -v
```

Генерация перезаписывает только свои результаты в `ml/prepared/`:

- `rows.jsonl` — одна строка JSON на пример; файл локальный, исключён из Git и воспроизводится командой выше;
- `manifest.json` — версии признаков/метки, SHA-256 источников, списки разрешённых столбцов, разбиение и ограничения;
- `review-examples.json` — небольшая подборка примеров **из train/pending**, без просмотра будущего тестового набора.

Исходный кейс и синтетическая история не меняются. Для иной истории/каталога запускать
подготовку заново, сравнивать hash и версии; смешивать результаты разных выгрузок нельзя.

## Единица наблюдения и метка

Строка: `(serviceId, predictionAt)`. Снимки ежедневно в **15:00 UTC**; это технический
режим подготовки, не утверждённое расписание админ-панели. Строка включается, если
видимые тогда статус `active`/`suspended`, договор и оплаченный срок удовлетворяют
`predictionAt < dueAt <= predictionAt + 7 суток`. Известная замена исключает старую VPS.

`cycleId = serviceId + dueAt` связывает несколько дневных наблюдений одного продления.
Метку определяем по **этому сроку**, а не по конечному состоянию VPS через несколько месяцев.
Дата завершения наблюдения — `labelDeadline = dueAt + 5 суток`, включительно.

| Метка | Условие |
|---|---|
| `0` | Есть успешная оплата именно этого цикла к `labelDeadline`, которая продлевает оплаченный срок; либо явная подтверждённая замена на VPS того же клиента |
| `1` | Полное окно наблюдения завершено, но оплаты и подтверждённой замены нет |
| `null` | История ещё не достигла `labelDeadline`; строка не допускается к обучению/оценке |

Даже если успешная оплата уже видна, ждём окончания полного окна для всех примеров:
иначе незрелые положительные исходы были бы отброшены, а ранние отрицательные оставлены.
Поздняя оплата **после** пяти суток не меняет метку этого окна на `0`.

Замена требует `replacement_linked` и существования новой VPS того же клиента;
обычная покупка ещё одной VPS не является доказательством замены. Upgrade и downgrade
одинаково дают `0`; уменьшение выручки при downgrade — другая задача.
В этой версии ограничиваем момент подтверждённой замены тем же `labelDeadline`.
Если бизнесу нужен более длинный период миграции, надо изменить версию метки до обучения.

`availableAt` — когда ответ допустимо использовать: не раньше конца grace и не раньше
регистрации всех событий-доказательств, включая создание новой VPS при замене.
Досрочная оплата/замена, зарегистрированная после прогноза, тоже даёт `0`, но не попадает
в признаки этого прогноза. `asOf` трактуется как граница **полной** истории, не просто
максимальная дата события. Для реальной выгрузки такую полноту должен гарантировать источник.

## Признаки v1 — 24 столбца

В модель в будущем попадут только `row.features`, по спискам из manifest. Остальные
поля строки — служебные метаданные, аудит и ответ; никогда не передавать CatBoost весь JSON.

| Столбцы | Определение |
|---|---|
| `status`, `payment_term`, `tariff_code` | Категории из событий, известных к прогнозу; не конечный снимок |
| `days_to_expiry` | Точные доли суток до оплаченного срока |
| `service_age_days`, `account_age_days` | Возраст VPS и клиента на момент прогноза |
| `observed_history_days` | Длина видимой истории услуги, не давность всей будущей выгрузки |
| `price_minor`, `monthly_revenue_minor` | Цена текущего договора и месячный эквивалент, целые евроценты |
| `renewal_cycles_90d`, `successful_renewals_90d` | Число наступивших сроков и оплаченных циклов за предыдущие 90 суток; первоначальная покупка не продление |
| `failed_cycle_share_90d` | Доля циклов хотя бы с одной неудачной попыткой; три повтора одного платежа не три цикла |
| `late_cycle_share_90d` | Доля циклов с поздней оплатой или уже наступившим сроком без видимой оплаты |
| `mean_paid_delay_hours_90d`, `max_paid_delay_hours_90d` | Средняя/максимальная задержка оплаты завершённых платежом циклов; неоплаченные не изображаются нулевой задержкой |
| `days_since_successful_renewal` | Давность последнего известного успешного продления |
| `recoveries_90d`, `contract_changes_90d` | Число восстановлений и изменений договора за 90 суток; начальный договор не изменение |
| `has_renewal_history` | Есть ли вообще предыдущие успешные продления |
| `history_30d_complete` | Доступен ли 30-дневный горизонт наблюдения портфеля; не гарантия полноты реального источника |
| `history_90d_complete` | Наблюдалась ли сама VPS не менее 90 суток |
| `live_vps_count`, `portfolio_monthly_revenue_minor` | Живые VPS и месячный эквивалент портфеля клиента на момент прогноза |
| `portfolio_change_30d_minor` | Изменение портфеля относительно состояния, **известного 30 суток назад** |

Для hour используется 720 часов, week — 30/7, календарных тарифов — деление на число
месяцев периода. Округление HALF_UP по услуге. Почасовой эквивалент — непрерывное
использование 30 суток, **не** месячная цена альтернативного договора из каталога.

`null` означает отсутствие данных, не отсутствие проблем. Например, у новой VPS доля
неудачных продлений неизвестна (`null`), число прошлых циклов — 0, `has_renewal_history` — 0.
В будущем адаптер CatBoost переведёт числовые `null` в NaN; сейчас никакого заполнения,
масштабирования или обучения преобразований на всей выборке не выполняется.

## Защита от утечек

При восстановлении состояния одновременно проверяются `occurredAt <= predictionAt`
и `recordedAt <= predictionAt`: событие произошло и уже поступило в систему.
Аудит строки содержит верхние даты использованных событий. Одного аудита недостаточно,
поэтому тесты меняют будущие события и убеждаются, что прошлые признаки не изменились.

Не читаем как исторические признаки:

- конечные `syntheticSnapshot` и `currentContracts`, баланс и `totalReplenished`;
- генераторные сценарии, причины событий, будущие статусы/оплаты/замены;
- ID клиента/услуги, `cycleId`, метки, даты доступности меток и доказательства;
- `autoProlong`: для него нет истории изменений;
- CPU/RAM/локацию из каталога: он наблюдался 24 октября, позже всей истории.

Код тарифа и цена сохранены в **синтетических исторических событиях договора**.
Это допустимые входы демонстрационного расчёта, но не свидетельство настоящих цен Aeza
в апреле. Для характеристик VPS нужен исторический снимок конфигурации в событиях договора;
не следует скрыто присоединять сегодняшний каталог и называть проверку исторически честной.
Регистрация клиента из `accountBusiness` считается неизменяемым фактом, известным с даты регистрации.

## Разделение по времени

- `train`: прогноз раньше 1 августа 15:00 UTC, и метка доступна **до** этой даты;
- `validation`: прогноз с 1 августа до 1 сентября 15:00 UTC, метка доступна **до** 1 сентября;
- `test`: прогноз с 1 сентября, полное окно наблюдения закончено;
- `purged`: прогноз попал перед границей, но его ответ пересекает границу — не используем;
- `pending`: исход пока неизвестен — не используем.

`validation` в будущем поможет выбирать параметры; `test` останется отдельной финальной
проверкой. Ни один цикл продления не пересекает train/validation/test. Старые клиенты
могут встречаться в более позднем периоде: проверяем прогноз будущего для существующей
базы, а не перенос на совершенно новых клиентов. Для последнего нужна отдельная проверка.

Повторные дневные строки одного цикла не независимые случаи. В метаданных есть
`cycleWeight = 1 / число строк цикла внутри его группы`, чтобы при будущем обучении
один цикл не получал семикратный вес только из-за семи дат наблюдения. Это не веса
классов и не денежные веса. Для ежедневного топ-K считаем уникальных клиентов в этот день.

## Что обсудить до обучения

1. По текущему буквальному определению прекращение по инициативе клиента и блокировка
   провайдером без оплаты тоже могут давать `1`. Отдельный пример блокировки включён
   в review-examples: для задачи удержания такой случай, возможно, следует исключать.
   Пока фильтрации по будущей причине нет, решение за пользователем.
2. Все почасовые строки этого набора ещё незрелые: даже их ранние прогнозы близки к
   концу истории. Дневной шаг также пропускает некоторые короткие почасовые циклы.
   Нельзя обучиться на месячных VPS и заявить проверенное качество для почасовых.
3. Синтетика воспроизводит правила генератора, а не реальные закономерности ухода.
   8 тысяч строк — не 8 тысяч независимых клиентов. Нужны реальные история и исходы
   прежде, чем интерпретировать оценку как качество на настоящем бизнесе.

Исходные тестовые данные и генераторы сохраняем. По договорённости тестовый код
удаляется только перед финальным PR, после проверок; сейчас он нужен для разработки.
