# Пошаговая симуляция и восстановление

Реализовано 25 октября 2026. Это ядро для живого worker, **не проигрыватель истории**.
Постоянный процесс, ускоренные часы и FastAPI чтение журнала теперь реализованы
в [generator_service](../../../generator_service/README.md). Consumer Kotlin и MinIO — следующий этап.
Модель, веса правил и исходные датасеты не менялись.

## Выполнение

`BehaviorSimulation.advance(until)` обрабатывает обе очереди до указанного UTC-времени
включительно и возвращает только новые наблюдаемые события. `step()` обрабатывает
ближайший момент времени целиком. `run()` использует тот же путь до конца горизонта.
Обработка равных timestamps сохраняет прежний порядок: биллинг, наблюдение результатов,
поведенческие реакции. Запланированное действие может создать следующие действия.

Внутренние очереди — `heapq`, один писатель состояния. Redis/Celery здесь не нужны.
Worker вычисляет границу виртуального времени и вызывает этот код;
HTTP GET не должен двигать симуляцию. Во время простоя виртуальное время стоит.
Догоняющий режим, если понадобится, должен включаться явно, а не возникать от рестарта.

## Что сохраняется

`checkpoint.py` сохраняет версионированный приватный JSON, не pickle:

- текущее время, начало и конец конечного горизонта;
- клиенты, общий баланс, услуги и наблюдаемый журнал;
- очередь биллинга и очередь намерений клиентов;
- счётчики событий/команд, реестр выполненных или поставленных команд;
- бюджетные расходы, ожидающие пополнения и ручные действия;
- планы замен и ограничений, потребности и поведенческие профили;
- состояние каждого потока `random.Random`;
- `runId`, номер сохранённой ревизии, версию схемы, Python major/minor,
  отпечаток кода движка и SHA-256 содержимого.

Это **не публичный снапшот**. В checkpoint есть скрытые причины и будущее;
его нельзя отдавать модели, фронту или складывать в публичную выгрузку.
Публичные события и снимки берутся только из уже сохранённой ревизии.

При загрузке проверяются checksum, версии, состав полей, порядок журнала и очередей.
Состояние кошельков/услуг сверяется с повторным применением наблюдаемых событий.
Код создания популяции не вызывается повторно; RNG восстанавливается без новых выборок.
Изменение кода движка или Python major/minor требует явной миграции checkpoint —
молчаливое продолжение с другими бизнес-правилами запрещено.

## Надёжность записи и границы гарантий

1. `flock` сериализует read-modify-write на одном хосте.
2. Новое состояние пишется во временный файл в том же каталоге, права `0600`.
3. `flush` и `fsync` сохраняют содержимое.
4. `os.replace` атомарно меняет checkpoint; затем вызывается `fsync` каталога.
5. Метод возвращает состояние только после записи.

До замены checkpoint читатель видит прежнюю ревизию, после — новую целиком.
Если процесс убит до замены, может остаться приватный `.checkpoint-*.tmp`;
он не считается сохранённым состоянием и не используется при восстановлении.
Ошибки записи не замалчиваются. При сбое после rename и до подтверждения нужно
перечитать checkpoint: нельзя предполагать, что операция обязательно откатилась.

Повтор `advance(until=T)` при уже сохранённой границе T не создаёт дубли и не меняет
ревизию. Для повторяемого `step()` вызывающий код передаёт `expected_revision`;
устаревшее значение вызывает `RevisionConflict`, а не второй шаг.
Идентичная команда с прежним ID остаётся идемпотентной после восстановления.

Поддержка: локальная POSIX-файловая система (Linux/macOS), доверенный persistent volume,
все писатели используют этот API. Это **не распределённая блокировка** и не гарантия
для нескольких серверов/NFS. SHA-256 обнаруживает повреждение, но не заменяет подпись
от злоумышленника с доступом к диску. Никакой внешний checkpoint не загружается по HTTP.

Журнал и диагностика пока хранятся целиком: размер checkpoint ограничен 128 MiB,
запись и проверка растут с историей. Для масштабирования потребуется отделить журнал
и сохранять более компактное состояние. При превышении лимита — явная ошибка, не потеря данных.

HTTP слой уже публикует committed журнал и позволяет повторять чтение по курсору.
Consumer Kotlin ещё должен сохранять курсор и дедуплицировать `(runId, eventId)`. Не следует называть
локальный checkpoint гарантией exactly-once HTTP-доставки.

## Запуск без веб-сервера

Из корня ML-репозитория, Python 3.13, без установки ML-зависимостей:

```sh
mkdir -p runtime
python3.13 -B examples/risk/event-driven/checkpoint.py \
  --checkpoint runtime/demo.json create --accounts 50 --days 1095 --seed 20261024

python3.13 -B examples/risk/event-driven/checkpoint.py \
  --checkpoint runtime/demo.json advance --until 2026-02-01T00:00:00Z

python3.13 -B examples/risk/event-driven/checkpoint.py \
  --checkpoint runtime/demo.json status

# Новый процесс продолжает следующий момент, а не запускает генерацию заново.
python3.13 -B examples/risk/event-driven/checkpoint.py \
  --checkpoint runtime/demo.json advance --expected-revision 1
```

Повтор `create` для существующего файла запрещён. Для продолжения — `advance`.
Каталог `runtime/` исключён из Git; нужен постоянный том, а не временный слой контейнера.

Проверенный пример с 5 клиентами и горизонтом 180 дней:

| Действие отдельного процесса | Ревизия | Виртуальное время | Событий |
|---|---:|---|---:|
| Создать | 0 | 2026-01-01 00:00 UTC | 0 |
| Продвинуть | 1 | 2026-02-01 00:00 UTC | 11 |
| Перезапустить и прочитать | 1 | 2026-02-01 00:00 UTC | 11 |
| Продолжить | 2 | 2026-03-01 00:00 UTC | 27 |

## Проверки

22 новых теста: различные seed и month/day/hour, произвольные границы шага,
запрет движения назад, повтор шага, восстановление в новом процессе, сохранение RNG,
ожидающих замен и ограничений, целостность checkpoint, атомарная запись, конкурирующие
процессы, SIGKILL до/после rename и сохранение идемпотентности команд.
Проверена неизменность **всей сохранённой lifecycle-v3 observations**, не только количества строк.

```sh
python3.13 -B -m unittest discover -s examples/risk/event-driven/tests
python3.13 -B -m unittest discover -s ml/tests -p test_event_driven_dataset.py
```
